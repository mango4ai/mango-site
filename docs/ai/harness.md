# 五、Harness

这个词在中文讨论里出现得少，但你一定用过它的产物——命令行里的 AI 编码工具、IDE 里的 AI 助手，都是 Harness。

**Harness（常译作"运行框架 / 装配层"）**：套在大模型外面、把它变成一个能干活的应用的那一层软件——负责**装配工具、管理上下文、驱动循环、划定权限、记录过程**。

一句话定义：**模型负责想，Harness 负责让它想得下去、干得出来、出事可控。**

## 为什么需要这一层

光有一个大模型 API，你得到的是"一个能接话的函数"。想让它真的完成工作，还缺一大堆东西：

| 缺的东西 | Harness 补上什么 |
| --- | --- |
| 它不知道你能干什么 | 把可用工具列成清单告诉它（工具注册表） |
| 它看不见你的项目 | 把相关文件内容自动装进上下文 |
| 它只回复一句话就停 | 驱动"思考—行动—观察"的循环持续跑 |
| 它可能乱删文件 | 权限控制、危险操作拦截、沙箱隔离 |
| 对话太长会爆窗口 | 上下文压缩、摘要、裁剪 |
| 出问题没法查 | 完整的执行日志与回放 |
| 每次都要重说一遍要求 | 项目级的持久配置（类似记忆文件） |

**打个比方：模型是发动机，Harness 是车架、传动、方向盘和刹车。** 发动机再强，没有车架也只是一堆零件在空转；而刹车的水平，决定了这辆车敢开多快。

## Harness 里通常有什么

1. **系统提示（System Prompt）**
   每次请求都带上的"岗位说明书"：你是谁、能用什么工具、什么能做、什么必须先问、输出什么格式。**它决定了这个 Agent 的性格和边界。**

2. **工具注册表**
   把"读文件、写文件、搜索、执行 shell、联网、调 MCP 服务"等能力，以结构化描述（名称 + 参数说明）交给模型，让它自行选择。

3. **上下文管理**
   这是 Harness 最见功力的地方：窗口有限，而项目很大。要决定**什么该装进来、什么该压缩成摘要、什么该丢掉**。装错了，模型就"看不见"关键代码，表现立刻变差。

4. **循环控制**
   驱动多步执行，并处理失败：工具报错要回传给模型让它重试；步数超上限要停下；任务完成要判断并退出。

5. **权限与安全边界**
   区分只读与写入操作，危险命令（删除、强制推送、发版）走人工确认，必要时放进容器 / 沙箱里跑。**这一层的厚薄，直接决定你能放心交给它多少。**

6. **可观测性**
   记录它每一步想了什么、调了什么工具、结果如何。没有这个，出问题只能靠猜。

7. **项目级配置**
   一个随项目走的说明文件（约定俗成叫 `AGENTS.md`、`CLAUDE.md` 之类），写清项目结构、构建命令、代码风格。**相当于给新同事的入职文档，模型每次开工前先读它。**

## 和其他几个词的关系

容易混淆，一张表摆清楚：

| 概念 | 是什么 | 类比 |
| --- | --- | --- |
| **Model（模型）** | 负责理解和生成的大脑 | 发动机 |
| **Harness** | 把大脑装成能干活的应用 | 车架 + 操控系统 |
| **Agent** | 由 Harness 驱动起来、正在跑的那个循环 | 正在开的车 |
| **MCP** | Harness 外接工具的标准插口 | 标准化的拖车挂钩 |
| **Skills** | 可插拔的"作业指导书" | 随车工具箱里的专用说明书 |

> 边界说明：这几个词在工程实践里没有严格统一的定义，不同厂商用法会有出入。**理解它解决的问题，比记住名词更重要。**

## 怎么判断一个 Harness 好不好

- **它能不能自己找到需要的文件**，而不是要你把代码全贴进去。
- **长任务会不会中途失忆**（上下文管理的质量）。
- **报错后能不能自己改**（循环和重试的质量）。
- **它要删东西时会不会先问你**（权限控制的水平）。
- **事后你能不能看清它干了什么**（可观测性）。

## 小结

**模型的能力决定上限，Harness 的水平决定你实际能拿到多少。** 同样的模型，套上不同质量的 Harness，实际干活的表现可以差好几倍——这也是为什么"换个工具用同一个模型，体验完全不一样"。
