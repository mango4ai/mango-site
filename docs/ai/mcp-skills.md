# 5. 连接篇：MCP、Skills 与工具生态

模型再聪明，连不上你的系统就只是个聊天窗口。这一层解决的是**"怎么接"和"怎么教"**。

## Function Calling：一切的起点

模型本身不能真的调用工具，它只能输出"我想调用 X 工具，参数是……"这样的结构化意图。真正执行的是外面的程序，执行完再把结果放回上下文。这个机制叫 **Function Calling（函数调用）/ Tool Use**。

它是单点的、要你在代码里手工声明的。一旦工具数量变多、要跨应用复用，就会变成"每个应用给每个工具写一遍适配"的 N×M 问题。**MCP 就是来消灭这个 N×M 的。**

## MCP：给 AI 装一个 USB 接口

**MCP（Model Context Protocol，模型上下文协议）** 是一套开放协议，规定 AI 应用与外部工具/数据之间怎么连、怎么列能力、怎么调用。类比：**AI 世界的 USB 接口**——设备（数据源、工具）做一次，主机（AI 应用）做一次，之后任意组合。

### 三个角色

| 角色 | 是谁 | 干什么 |
| --- | --- | --- |
| **Host（宿主）** | 用户直接用的 AI 应用（桌面端、IDE 插件、命令行 Agent） | 发起连接、把能力交给模型、管权限和确认 |
| **Client（客户端）** | Host 内部的协议实现 | 与某个 Server 建立并维护一条连接 |
| **Server（服务端）** | 某个具体系统（数据库、文件系统、Git、Jira、内部 API）的适配器 | 对外暴露自己的能力并执行调用 |

### Server 能暴露的三类东西

- **Tools（工具）**：可以被调用的动作，例如"查询订单""创建 issue""执行 SQL"。这是最常用的部分。
- **Resources（资源）**：可以被读取的内容，例如文件内容、数据库表结构、文档片段。
- **Prompts（提示模板）**：预置的提示词模板，用户或模型可以直接套用。

连接建立时双方会做**能力协商**（各自支持什么），之后按协议双向通信。传输方式既有本地进程间的标准输入输出（适合连本地文件、本地数据库），也有基于 HTTP 的远程方式（适合连云端服务）。

### 为什么值得关心

- **一次接入，到处可用**：写一个 MCP Server，所有支持 MCP 的 AI 应用都能用。
- **边界清晰**：Server 决定暴露什么、不暴露什么，权限收敛在 Server 侧，Host 侧再叠加一层人工确认。
- **生态复用**：社区已有大量现成 Server（Git、数据库、浏览器、各类 SaaS），不必自己造。

::: warning 别忽略安全
MCP Server 拿到的权限就是它能闯的祸。连接第三方 Server 前看清它申请了哪些能力；能读写的目录尽量收窄；涉及删除、付款、外发消息的动作，务必保留人工确认。
:::

## Skills：把"怎么干"沉淀成说明书

MCP 解决**能不能做**（能力），Skills 解决**会不会做**（方法）。

**Skill（技能）** 的最小形态就是一个文件夹 + 一个 `SKILL.md`：

```text
my-skill/
├── SKILL.md        # 必需：元数据 + 操作说明
├── scripts/        # 可选：配套脚本，确定性的活交给代码
└── resources/      # 可选：模板、参考资料
```

`SKILL.md` 通常是 **YAML frontmatter + Markdown 正文**：

- frontmatter 里的 `name` 和 `description` 是给模型的**索引**：我用得上吗？
- Markdown 正文是**真正被加载的操作说明**：步骤、检查项、输出格式、常见坑。需要时再附带上脚本和参考资料。

### 核心机制：渐进式披露

模型不会一次性把所有技能的全文塞进上下文（那会撑爆窗口）。它分三级加载：

1. **索引**：始终只加载所有技能的 `name` + `description`，成本极低。
2. **正文**：判断某个技能与当前任务相关时，才把它的 `SKILL.md` 正文读进来。
3. **附件**：正文里引用到的脚本、模板、参考资料，用到再读。

好处是**技能可以很多，但只有相关的占用上下文**。这也是为什么写 Skill 时，`description` 的质量比正文更重要——它决定技能会不会被想起来。

### Skill 与 MCP 怎么配合

- **MCP 提供手**：能查数据库、能发请求。
- **Skill 提供套路**：这次该查哪张表、按什么顺序查、结果怎么校验、报告怎么排版。

举例：MCP 接上了公司的数据库，Skill 则写下"月度经营分析"的固定流程——先取哪些指标、口径怎么算、异常怎么标注、最后输出什么格式。前者是可复用的连接，后者是可复用的经验。

## 一图总结这四层

```text
模型（大脑：决定下一步做什么）
 └── Harness（外壳：循环、权限、上下文、日志）
      ├── MCP（接口：标准化的工具与数据源）
      └── Skills（经验：怎么把这件事做对）
```

## 还不懂的地方

- 工具数量很多时（几十上百个），模型常常选错工具。目前的缓解办法是分层：先按类别检索，再把少量候选交给模型。
- 多个 MCP Server / 多个 Skill 之间如何优雅协作与冲突消解，还没有成熟共识。
