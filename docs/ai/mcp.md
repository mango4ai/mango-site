# 六、MCP

**MCP（Model Context Protocol，模型上下文协议）**：一套开放的通信协议，**规定 AI 应用和外部数据源 / 工具之间怎么对话**——怎么发现有哪些能力、怎么调用、怎么传结果。

一句话定义：**MCP 是 AI 世界的 USB-C。**

## 为什么需要它

没有 MCP 的时候，状况是这样的：

- 有 N 个 AI 应用（各种客户端、编辑器、命令行工具）
- 有 M 个外部系统（数据库、代码仓库、日历、企业内部接口）
- 要让它们互相配合，每个应用都得为每个系统**单独写一份适配代码** → **N × M 的工作量**

有了 MCP：

- 外部系统一侧**只实现一次** MCP 服务端，对外暴露标准接口
- AI 应用一侧**只实现一次** MCP 客户端，就能连上所有服务端
- 工作量变成 **N + M**

**谁受益**：写工具的人不用逐个适配各种 AI 应用；用工具的人不用等官方支持，自己接一个就能用。

## 三个角色

| 角色 | 是什么 | 例子 |
| --- | --- | --- |
| **Host** | 用户直接使用的那个 AI 应用，负责发起连接 | 编辑器、桌面客户端、命令行 AI 工具 |
| **Client** | Host 内部的连接器，一个 Client 对应一个 Server | 由 Host 实现，用户看不到 |
| **Server** | 把某个外部系统的能力按 MCP 规范暴露出来的小程序 | 文件系统服务、数据库服务、内部接口服务 |

## Server 能提供什么

MCP 把能力分成三类：

1. **Tools（工具）**
   **模型可以主动调用的动作**，可能有副作用。比如"执行这条 SQL 查询""创建一条工单""提交一个 PR"。
   → 这是最常用的一类。

2. **Resources（资源）**
   **可以被读取的内容**，通常是只读的。比如文件内容、数据库表结构、接口文档。
   → 相当于给模型开了一排可翻阅的资料柜。

3. **Prompts（提示模板）**
   Server 预置的常用提示词模板，用户或模型可以取用。
   → 把"这个系统该怎么问"的最佳实践打包分发。

## 怎么连

两种主流传输方式：

- **stdio（标准输入输出）**：Server 作为本地子进程启动，通过标准输入输出通信。**配置简单、无需网络，本地工具最常用。**
- **HTTP / SSE**：Server 作为远程服务，通过网络访问。**适合企业级部署和多人共享。**

典型配置就是一段 JSON：告诉 Host "启动这个命令，就得到一个 MCP 服务"。配好后，它提供的工具会和内置工具一起出现在模型的工具清单里，模型自己决定什么时候用。

## 一个完整的例子

给 AI 助手接一个"公司内部工单系统"的 MCP Server：

1. 你写好一个 MCP Server，暴露三个 Tools：`查询工单`、`创建工单`、`更新工单状态`，以及一个 Resource：`工单字段说明`。
2. 在 AI 应用的配置里加上这个 Server（一行命令）。
3. 你说："把上周标记为 P0 但还没关闭的工单列出来，写个周报。"
4. 模型看到工具清单里有 `查询工单`，自己调用它 → 拿到结果 → 整理成周报。
5. 你说"顺手把 #1234 关掉"，模型调用 `更新工单状态`。

**关键点：你没写任何胶水代码，也没教它怎么用。** 它读工具描述就知道该在什么时候用。

## 需要注意什么

- **MCP 只解决"怎么连"，不解决"该不该做"。** 权限、审批、审计仍由 Host 和你自己负责。
- **工具不是越多越好。** 几十个工具塞进上下文，模型会挑花眼，还会挤占窗口。**只启用当前任务需要的。**
- **Server 来自第三方时，等于你把一部分执行权交给了它。** 尽量用官方或可信来源，看清它到底能做什么。
- **工具描述的质量直接决定调用效果。** 描述写得含糊，模型要么不用，要么乱用。

## 和 Skills 的区别

经常被放在一起问，简单区分：

- **MCP 提供"能力"**——能触达到哪个系统、能做什么动作。
- **Skills 提供"方法"**——拿到能力之后，这类事情的标准流程是什么。
