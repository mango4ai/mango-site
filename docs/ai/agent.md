# 4. Agent 篇：从聊天机器人到会干活的数字员工

## Chatbot 和 Agent 的区别

- **Chatbot**：你问一句，它答一句。它只能"说"，不能"做"，而且答完就忘。
- **Agent（智能体）**：你给一个目标，它自己**拆步骤 → 调工具 → 看结果 → 修正 → 继续**，直到把事办完或明确办不了。

一句话：**Chatbot 的输出是文字，Agent 的输出是结果。**

## Agent 的最小结构

```text
目标（用户的需求）
  ↓
规划：拆成若干步骤
  ↓
行动：调用工具（搜索 / 读文件 / 执行代码 / 发请求）
  ↓
观察：拿回工具返回的结果
  ↓  ↺ 不满意就回到"规划"重来
完成：给出结论或产物
```

这个"思考—行动—观察"的循环，常见叫法有 ReAct 循环、Agent Loop。**循环是否收敛，是 Agent 是否可用的分水岭**——转不出来就变成烧钱的死循环。

## 三个关键零件

1. **工具 Tools**：Agent 的手和脚。常见有网页搜索、文件读写、代码执行（沙箱）、数据库查询、第三方 API。工具描述写得清不清楚，直接决定模型会不会用对。
2. **记忆 Memory**：短期记忆是上下文窗口里的对话与工具结果；长期记忆要靠外部存储（向量库、数据库、笔记文件）把关键信息捞回来塞进上下文。
3. **规划 Planning**：把大目标拆成可执行的小步骤，并在失败时改道。复杂任务常用"先规划再执行"或"边做边规划"。

## Harness：被低估的那层

**Harness（本意"挽具/线束"）** 指包裹在模型外面、驱动它干活的那套运行时外壳。模型只负责"下一步该干什么"，真正让它动起来的是 Harness：

- **循环控制**：什么时候继续、什么时候停、最多转几圈。
- **工具调度**：把模型想调用的指令翻译成真实调用，并把结果按格式塞回去。
- **上下文管理**：裁剪历史、压缩长结果、把重要信息提到前面，防止窗口撑爆。
- **权限与安全边界**：哪些文件能读写、哪些命令要人工确认、能不能联网。
- **可观测性**：把每一步的思考、调用、耗时记下来，出错时能复盘。
- **人机协同**：高风险动作停下来问人，让人随时接管。

同一个模型，套上不同的 Harness，表现可以从"聊得挺好"变成"真能把活干完"。**Agent 产品的差距，很大一部分不在模型，而在 Harness。**

## 一个具体例子

> 目标：把这个仓库里所有 TODO 注释整理成一个清单，按文件分组，输出 Markdown。

没有 Agent：你手动搜索、复制、整理。
有 Agent + Harness：它列出文件树 → 读取源码 → 正则匹配 TODO → 汇总 → 写文件 → 把改动给你确认。中间读文件是工具，写文件是受权限约束的工具，每一步都留痕。

## 现在的真实局限

- **长任务会漂移**：步骤一多，模型容易忘记最初目标，需要显式地重述目标与进度。
- **错误会累积**：一步做错，后面全建立在错误之上，所以关键步骤要有校验。
- **成本不可控**：循环 + 长上下文，一次任务可能消耗大量 token，必须设上限。
- **权限是双刃剑**：给得太多有风险，给得太少干不了活。默认最小权限 + 高风险人工确认，是目前的通行做法。
- **评估困难**："干得好不好"往往没有客观标准，需要人工抽检或设计验收用例。

## 还不懂的地方

- 如何系统性地保证长任务不跑偏（目前主要靠流程设计和人工介入）。
- 多 Agent 协作（一个总控带几个专职）在什么规模下才真的划算。
