# 3. 大模型时代：LLM、Agent、Harness、MCP、Skills

这一页是全篇的重点。五个词听起来都像新概念，其实它们解决的是**同一个问题的不同层**：

> 怎么让一个"只会预测下一个字"的模型，变成能真的帮你把事办完的东西？

## 先看整体分层

```text
┌──────────────────────────────────────────┐
│ Skills    ：把"怎么做事"沉淀成可复用的说明 │
├──────────────────────────────────────────┤
│ Agent     ：定目标、自己规划、调用工具、收尾 │
├──────────────────────────────────────────┤
│ Harness   ：跑起 Agent 的那层外壳/运行时    │
├──────────────────────────────────────────┤
│ MCP       ：把外部工具和数据源接进来的接口   │
├──────────────────────────────────────────┤
│ LLM       ：底层的大脑，负责理解和生成       │
└──────────────────────────────────────────┘
```

从上往下是"越来越贴近业务"，从下往上是"越来越底层"。下面逐个展开。

## LLM：大模型

**LLM（Large Language Model，大语言模型）** 是用海量文本训练出来的深度学习模型。它做的事，本质上极其简单：

> 给你前面这段话，预测下一个最可能的 token 是什么。

然后不断重复这个过程，就"生成"了一整段回答。

### 为什么这么简单的机制看起来很聪明

因为训练数据足够大（几乎整个互联网的文本），模型被迫学会了语言背后的**规律、知识和推理模式**——这些全都编码在它的参数里。所以它是"压缩了世界知识"的东西，而不是一个数据库。

### 它的三个关键特性

| 特性 | 说明 |
| --- | --- |
| 上下文窗口 | 一次能"看到"的 token 上限。超了就会忘掉前面的内容。这是最硬的约束 |
| 只会生成，不会执行 | 它输出的是文字。要真的发邮件、改文件、查数据库，得有人替它执行 |
| 会幻觉 | 它追求"说得通顺合理"，不保证"说的是真的"。不知道的时候也可能编一段很像样的内容 |

::: warning 最重要的一条认知
大模型**不知道自己不知道什么**。它给出的答案，格式越工整、语气越确定，越不代表它是对的。关键信息必须验证。
:::

### 怎么让它干活：从"问一句"到"给足上下文"

模型的表现几乎完全取决于你给它的输入，所以有了一整套围绕输入的学问：

- **提示词（Prompt）**：把要求说清楚——给角色、给背景、给示例、给输出格式
- **上下文工程（Context Engineering）**：更进一步的思路——既然模型只看得到上下文，那就**系统性地设计每次请求里装什么**：历史消息怎么截断、参考资料怎么塞、工具结果怎么回写
- **少样本示例（Few-shot）**：给几个例子，比讲一堆要求有效

## Agent：智能体

**Agent（智能体）** 是为 LLM 补上"手和脚"的一种结构。区别就在：

| | 普通聊天 | Agent |
| --- | --- | --- |
| 你给一句，它答一句 | ✅ | ✅ |
| 它能自己查资料、调用工具 | ❌ | ✅ |
| 它能分步规划、失败了换个办法重试 | ❌ | ✅ |
| 你定目标，它把整件事做完 | ❌ | ✅ |

一个 Agent 的基本循环只有四步：

```text
1. 看：拼好上下文（目标 + 已做过的事 + 可用工具）
2. 想：LLM 决定下一步——直接回答，还是调用某个工具
3. 做：执行工具调用（读文件、跑命令、搜网页、调 API）
4. 回：把结果写回上下文，回到第 1 步，直到任务完成
```

::: tip 一句话理解
Agent = **LLM（大脑）+ 工具（手脚）+ 循环（能持续推进）**。
:::

### 相关的几个词

- **工具调用（Tool Use / Function Calling）**：模型不直接执行，而是输出"我想调用 XX 工具，参数是 YY"，由外部程序真的去执行
- **RAG（检索增强生成）**：回答前先去你的资料库里检索相关内容，塞进上下文再生成——专治"模型不知道你的私有信息"和幻觉
- **多模态**：输入输出不再只有文字，还能处理图片、音频、视频

## Harness：承载 Agent 的那层外壳

**Harness**（直译"挽具/ harness"，中文常译作"运行框架""外壳""宿主"）是**包在模型外面、让 Agent 真正跑起来的那一层软件**。

模型本身只输出文字，谁来执行工具？谁来记住历史？谁来防止它删错文件？——都是 Harness。

| Harness 负责的事 | 具体是什么 |
| --- | --- |
| 拼装上下文 | 把系统提示、工具说明、历史消息、检索结果组织成每次发给模型的请求 |
| 执行工具 | 收到模型的调用请求后真的去跑，再把结果回写 |
| 控制循环 | 决定最多跑几轮、什么时候停下、卡住了怎么办 |
| 权限与安全 | 哪些目录能改、哪些命令能跑、危险操作要不要人确认 |
| 观测与记录 | 日志、成本统计、出错时的可追溯性 |
| 模型无关 | 底层换成另一个模型，上层流程不用改 |

::: tip 为什么这个概念值得单独记
同一个模型，套在不同的 Harness 里，能干的事差别巨大。很多时候"这个 AI 好不好用"，瓶颈不在模型，而在 Harness——它决定了模型能触及什么、被允许做什么、上下文被组织得多好。
:::

::: details Harness 具体长什么样
日常用的 AI 编程助手、命令行 Agent、各种"AI 工作台"，除去模型本身，剩下那一大坨就是 Harness：它管着你的工作目录、能跑哪些命令、怎么问你要权限、怎么把结果展示给你。
:::

## MCP：把工具接进来的统一接口

**MCP（Model Context Protocol，模型上下文协议）** 是一套开放协议，规定"外部工具和数据源"应该怎么暴露给模型。

### 它解决什么问题

在 MCP 之前，想让模型用上你的数据库、你的内部系统，得为**每个模型 × 每个数据源**各写一遍对接代码——M 个模型配 N 个工具，就是 M×N 份工作。

MCP 把这件事标准化：工具按统一的格式描述自己，任何支持 MCP 的客户端都能直接连。

```text
没有 MCP：  模型A ─┬─ 工具1        （每对单独接线）
                   └─ 工具2
            模型B ─┬─ 工具1
                   └─ 工具2

有了 MCP：  模型A ─┐
            模型B ─┼─ MCP ─ 工具1 / 工具2 / 数据源N
            模型C ─┘
```

::: tip 公认的类比
MCP 之于 AI 应用，有点像 **USB-C 之于外设**：设备厂商按同一个标准做接口，主机厂商按同一个标准留口子，两边不用互相认识也能插上。
:::

### 三个角色

| 角色 | 是什么 | 举例 |
| --- | --- | --- |
| Host / Client | 用工具的那一边，通常是 Agent 或 AI 应用 | AI 编程助手、桌面客户端 |
| Server | 提供能力的一方，把自己的工具和数据按协议暴露出来 | 数据库 MCP server、文件系统 MCP server |
| Transport | 两者之间的通信方式 | 本地 stdio、HTTP |

Server 能提供的不只是"函数"，通常包括三类：**工具**（可执行的操作）、**资源**（可读的数据）、**提示词模板**（预设好的用法）。

## Skills：把经验沉淀成可复用的能力

模型"什么都会一点"，但**不知道你团队的规矩**：代码怎么组织、报告什么格式、评审看哪些点。每次都从头讲一遍，既费 token 又不稳定。

**Skills（技能）** 就是把"怎么做某件事"打包成一个可复用、可版本管理的单元，需要时再加载给模型。

一份 Skill 通常包含：

- **什么时候用**：一段简短描述，让模型自己判断该不该调用
- **怎么做**：步骤、规范、检查清单、注意事项
- **配套资产**：脚本、模板、示例文件

::: tip 关键设计：按需加载
Skill 不会全部塞进上下文（那样会撑爆窗口、互相干扰），而是**先只给模型看一份目录，命中了才把详细内容加载进来**。用有限的上下文换来了几乎无限的"可挂载能力"。
:::

### 和相邻概念的区别

| 概念 | 粒度 | 解决什么 |
| --- | --- | --- |
| Prompt | 一句话/一段话 | 这一次怎么问 |
| Skill | 一个可复用的任务包 | 这类活儿以后都这么干 |
| MCP | 一个外部能力接口 | 让模型能碰到外面的系统和数据 |
| Agent | 一个会自己推进的角色 | 把目标拆开、跑完、收尾 |

## 五者怎么协作：一个具体例子

需求：**"把上周的销售额整理成一份周报发给团队。"**

```text
1. Skills    命中"写周报"技能：规定了格式、口径、必填项
2. Agent     拆解步骤：取数据 → 算环比 → 生成图表 → 写结论 → 发送
3. MCP       通过数据库 MCP server 取到销售数据
4. Harness   执行查询、把结果回写上下文、发送前请求人工确认
5. LLM       负责理解需求、组织语言、写出结论
```

每一层都在做别人做不了的事：**LLM 负责理解，MCP 负责连接，Harness 负责执行与安全，Agent 负责推进，Skills 负责经验。**

## 常见误区

| 误区 | 实际情况 |
| --- | --- |
| "换个更强的模型就行了" | 很多时候瓶颈在上下文组织和工具权限，即 Harness 层 |
| "Agent 能全自动，不用管" | 越是关键操作越要留人工确认，这是 Harness 的职责 |
| "接上 MCP 就什么都能干了" | MCP 只是接口标准，工具本身好不好用是另一回事 |
| "写个 prompt 就够了，不用 Skills" | 一次性的事写 prompt；反复干的事值得沉淀成 Skill |

## 这一页记住三句话

1. **LLM 是大脑**：只会生成文字，不知道自己不知道什么。
2. **Agent + Harness 让它能动手**：Agent 负责"想下一步做什么"，Harness 负责"真的去做、并保证安全"。
3. **MCP 和 Skills 是可插拔的扩展**：MCP 解决"连得上"，Skills 解决"做得对"。
