# 七、Skills

**Skills（技能）**：把某类任务的**做法**（步骤、规范、检查清单，以及配套脚本和模板）写成一份结构化文档，**让模型在需要的时候自己取用**。

一句话定义：**Skills = 写给模型的岗位作业指导书，需要时才翻开，平时不占它的脑子。**

## 它解决什么问题

模型很聪明，但有两个老毛病：

1. **不知道你们家的规矩。** 你们发布要走什么流程、代码风格是什么、周报模板长什么样——它没见过，每次都得重新讲。
2. **上下文很贵。** 你要是把所有规矩一次性塞进系统提示，窗口被占满，模型反而变笨。

Skills 的解法是**渐进式加载**：

```
第 1 层：只加载所有 Skill 的名字和一句话简介（很便宜，常驻）
          ↓ 模型判断"这个任务好像跟某条对得上"
第 2 层：加载那份 Skill 的正文（步骤、规范、注意事项）
          ↓ 需要时
第 3 层：读取它附带的脚本 / 模板 / 参考文件
```

**好处是"按需付费"**：一百个 Skill 放着也不占地方，用的那一个才真正进上下文。

## 一个 Skill 长什么样

最小形态就是一个 `SKILL.md` 文件，开头用 YAML 写元信息，下面写正文：

```markdown
---
name: 发布周报
description: 从工单系统拉取本周进展，按团队模板生成周报。用于"写周报""本周总结"等请求。
---

# 发布周报

## 适用场景
用户要求写周报 / 本周总结 / 进展汇报时使用。

## 步骤
1. 调用工单工具，查询本周（周一至今天）已关闭和新增的工单。
2. 按"已完成 / 进行中 / 风险"三类归类。
3. 套用 `template.md` 里的格式输出。
4. 风险项必须写清责任人和预计解决时间。

## 注意
- 只统计本周有更新的工单，不要列出历史遗留。
- 数字必须与工具返回的原始数据一致，**不要估算**。
- 缺少信息时写"待补充"，不要编。
```

除了 `SKILL.md`，一个 Skill 还可以带上：

- **脚本**：确定性的活交给代码做（排序、格式转换、批量改名），比让模型手搓可靠。
- **模板 / 参考文档**：输出格式、字段定义、示例。
- **资源文件**：只在真正需要时才被读取。

## 和别的机制怎么区分

| | 是什么 | 什么时候用 | 谁触发 |
| --- | --- | --- | --- |
| **系统提示** | 常驻的岗位说明书 | 所有任务都要遵守的通用规则 | 一直生效 |
| **普通提示词** | 你当场说的一句话 | 一次性的、临时的要求 | 你 |
| **Skill** | 可复用的作业指导书 | **某类反复出现的任务** | **模型自己判断** |
| **MCP 工具** | 触达外部系统的能力 | 需要真的去操作系统时 | 模型自己判断 |
| **项目记忆文件** | 项目背景与约定 | 每次开工前了解项目 | 一直生效 |

一句话：**系统提示管"你是谁"，Skill 管"这类活怎么干"，MCP 管"你能碰到什么"。**

## 什么时候该写一个

出现下面任一情况，就值得沉淀成 Skill：

- **同一件事你已经跟它解释过三遍以上。**
- 流程有明确步骤，而且**错了代价不小**（发布、数据处理、对外文档）。
- 输出有固定格式要求（模板、表格结构、字段规范）。
- 需要团队里其他人和 AI 保持同样做法。

## 写好一个 Skill 的经验

- **`description` 是最关键的一行。** 模型靠它判断要不要用。**写清楚"什么时候该用"，而不只是"它能干什么"**——很多 Skill 没被触发，都是因为描述写得太抽象。
- **步骤要可执行**，别写成"认真分析一下"这种正确的废话。
- **把确定性的事交给脚本**，让模型专注在判断上。
- **明确写出反例**："不要……"，比只写"要……"有效得多。
- **保持小而专。** 一个 Skill 干一类事，别写成万能手册——太大就退化成一份没人读的文档。
- **写完试三次**：换几种说法提出同一个需求，看它每次都能自己认出来。认不出来的，回去改描述。

## 小结

**模型的能力是通用的，Skills 让它按你的规矩干活。** 这是从"会用 AI"到"把 AI 用成团队资产"的一步：你积累的不再是聊天记录，而是一份越用越值钱的作业手册。
