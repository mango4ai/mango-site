# Agent 与 Harness

## 什么才算 Agent

聊天机器人只是"输入 → 输出"。**Agent 会为了达成目标，自己决定下一步做什么，并真的去执行。**

最小公式：

```text
Agent = 模型（负责想） + 工具（负责做） + 循环（负责一直做下去）
```

一次典型的循环：

```text
目标 → 观察现状 → 模型决定下一步 → 调用工具 → 拿到结果
  ↑                                            │
  └────────────────────────────────────────────┘
              没完成就继续转
```

关键是那个**回环**：工具返回的结果会重新进入上下文，模型据此调整计划。没有回环的"一次性调用几个工具"不算真正的 Agent。

## 工具调用是怎么发生的

模型本身不能执行任何东西。流程是这样的：

1. 你把所有工具的**名字、参数说明、用途**放进上下文。
2. 模型输出一段结构化的"我想调用 X 工具，参数是 Y"。（这就是 function calling / tool use）
3. 外面的程序真正执行，把结果作为一条新消息塞回上下文。
4. 模型看到结果，决定继续调用还是收尾回答。

所以工具描述写得清不清楚，直接决定模型会不会用、用得对不对。**工具说明是给模型看的文档，不是给同事看的注释。**

## Harness：真正拉开差距的那层

Harness（直译"挽具、脚手架"）指的是**包在模型外面、驱动它干活的那套系统**。模型是引擎，Harness 是整套车架、传动和仪表盘。

它通常负责：

| 职责 | 具体做什么 |
| --- | --- |
| 上下文组装 | 把系统提示、工具定义、历史、检索结果拼成一次请求 |
| 工具注册与执行 | 定义有哪些工具，真正跑起来，处理报错和超时 |
| 权限与沙箱 | 哪些操作要人确认，命令在什么隔离环境里跑 |
| 上下文管理 | 超限后压缩、摘要、裁剪，防止"聊崩" |
| 重试与纠错 | 工具报错时把错误原样喂回去让它自己改 |
| 可观测性 | 记录每一步输入输出的日志，方便复盘 |
| 子任务编排 | 拆分任务、并行、交给子 agent |

**同一个模型，套上不同 harness，效果可以差一大截。** 这就是为什么各家 CLI 编码工具的能力差异，不全是模型本身造成的。

实际例子：Claude Code、Codex CLI、各类 IDE 里的编程模式，本质都是"模型 + 一整套面向代码库的 harness"。

## Agent 常见的翻车方式

- **目标含糊**：给它"把这个项目优化一下"，它就会开始乱改。→ 把验收标准写清楚。
- **工具返回太糙**：返回一大坨无关日志，上下文瞬间被污染。→ 工具要返回精炼、结构化、有 action 建议的结果。
- **上下文膨胀**：几十轮之后信息互相打架。→ 设定轮数上限，定期压缩，长任务拆成子 agent。
- **权限给太大**：直接允许删库删分支，一次误判就是事故。→ 破坏性操作必须人工确认，重要操作留可回滚的痕迹。
- **错误静默**：工具失败但没把错误喂回去，模型就以为成功了。→ 错误一定要可见。

## 多 Agent 什么时候值得用

把一个大任务拆给多个子 agent，好处是**上下文隔离**（每个子 agent 只看到自己那部分），坏处是**协调成本和结果不一致**。

值得拆的信号：任务可以明确切成互不重叠的块；单 agent 上下文已经快撑满；需要并行提速。

不值得拆的信号：任务本身是一条串起来的推理链；子任务之间频繁依赖彼此的中间结论。
